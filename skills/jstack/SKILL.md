# jstack

Choose the smallest useful route across the public suite and the user's configured private catalogs. Load the selected skill and carry the requested work to its acceptance evidence. The router coordinates capabilities; it is not a background worker, tool connection, or permission grant.

## Discover the permitted catalogs

Use the profile supplied for this task; otherwise check the documented local profile at `~/.config/jstack/profile.json` when available. An explicit profile replaces the default rather than silently merging it. Without a configured private catalog, use the verified public suite and identify any requested private route that remains unavailable. Do not scan private folders, workspaces, accounts, or memory stores to invent a catalog.

Read the profile and catalog summaries first, then only the selected entrypoints and relevant references. This discovery is limited to routing the current task; catalog access does not grant blanket private-content access or live effects. Follow [the catalog contract](references/catalogs.md) for versions, paths, identity, scope, provenance, and optional aliases/capabilities. The bundled [profile example](assets/profile.example.json) and [catalog example](assets/catalog.example.json) contain fictitious configuration, not working connections.

Prefer the user's explicit qualified entry or skill selection. Otherwise prefer a relevant specialist whose project, organization, or personal scope actually matches the task, ahead of a generic public fallback. A broad catalog container does not make all its scoped entries applicable. Resolve equally applicable names with the smallest material clarification; do useful independent work meanwhile. Never select another organization or an unrelated namesake because its name matches.

## Use the public suite where it fits

Honor an explicitly selected skill unless a concrete mismatch prevents the task. These public roles are available when discovered, and provide generic fallbacks where applicable. A simple task can stay with one specialist, and work outside this suite can use the appropriate existing workflow directly. Do not create a business operation, sprint, campaign, or ticket merely to use more skills.

| Skill | Route here when the outcome needs… |
| --- | --- |
| `one-person-company` | Ownership of a whole business outcome, shared resources, initiatives, and continuing customer responsibilities |
| `remember` | An explicit durable save, correction, forgetting request, or relevant recall from an established memory store |
| `software-factory` | Software delivery through review and verification, or engineering of that delivery system |
| `marketing-factory` | An end-to-end campaign or measurable marketing experiment, including outcome interpretation |
| `web-publisher` | Static hosting, site release, protected content, access verification, or publishing recovery |
| `scrum-master` | Story readiness, estimation, backlog or sprint decisions, standup, review, or retrospective |
| `ad-buying` | Paid-media analysis, creative preparation, paused campaign construction, or an authorized launch |

Use `one-person-company` for the cross-functional operating mandate, not every business task. Ad reporting can go directly to `ad-buying`; a static release can go directly to `web-publisher`; a preference mentioned during another task need not be saved. Add another skill only for a real dependency or requested result.

When creating or extending a publisher, prioritize the intended project repository before cloud provisioning or a standalone uploader. Reuse an applicable repository-backed specialist; otherwise have `web-publisher` establish source/build ownership, a release ref, artifact provenance, and shared deployment coordination. Multiple agents need isolated source work and a real shared release claim, with stale-release and uncertain-write handling; a checkout-local lock is insufficient. Keep account-specific bindings in the private project, not this public router.

## Resolve the actual skill and context

Resolve the selected catalog entry, host catalog result, or verified suite checkout to its actual `SKILL.md`. Before executing, verify its description, source, scope, and any declared entrypoint hash. A matching name alone does not prove it is the intended public export or private variant. A supplied public companion folder may take precedence over a global namesake only after its suite provenance is verified. Reuse a verified source within the current work unless it changes; source drift reopens the affected selection and acceptance.

Do not assume the router archive includes its companions, all skills are installed, or integrations exist. If a required skill or relevant private catalog is missing, identify the gap and continue useful authorized preparation, labeling fallback work honestly. Hold private or account-specific effects when the intended scoped route cannot be verified; do not substitute a generic workflow that guesses its account, authority, or private inputs. Use existing setup authority when installation is part of the request, and never claim the missing workflow ran.

Keep project facts, identities, budgets, and grants in the project's supplied private configuration. A configured, context-matching private route can be the correct primary route; it is not a lesser fallback. Each handoff still needs its own applicable scope and authority. Keep private catalog details, source paths, selected skill content, and task inputs out of public artifacts or output; use a public-safe role label when needed. A visibility label does not declassify source data.

## Chain only the required capabilities

For work spanning skills, name one outcome coordinator and the owner of each deliverable. A business operation can coordinate several initiatives; a marketing experiment can own a landing-page dependency; a software change can request a publishing step. Keep the existing authoritative queue and records. Skill calls are not automatically new tickets or owners.

State a short route and the next acceptance checkpoint, then execute the useful work. Planning does not require another confirmation when the task already authorizes execution. Follow [chaining and recovery](references/chaining.md) for dependencies, shared resources, and resumed work. Use [the handoff template](assets/handoff.md) when an edge needs a durable record; a small chain can keep the same information inline.

Order dependent steps by their required inputs and run independent work in parallel when useful. Same-session sequencing is sufficient; do not require subagents, new chats, or messages for every handoff. Delegate only with supported tools and the applicable authority, preserving the selected skills' review independence where required.

Accept each returned artifact against the requested input contract, revision, and evidence before dependent effects. A prepared page does not establish a deployed page; a deployed page does not establish valid tracking; approved creative does not establish a live campaign or a measured outcome. Reopen affected downstream acceptance when an input changes.

## Preserve limits and finish the loop

Carry the user's existing grants forward without asking again within unchanged scope. Routing, a handoff, a stored note, and a successful review do not create missing authority for publication, spending, messages, memory writes, or recurring work. Share one resource envelope across the chain; never multiply the parent budget across nodes or reset limits by selecting another skill.

Before retrying or rerouting an uncertain external action, reconcile its original receipt and actual remote state. Hold the affected edge when its outcome, authority, required input, or remaining resources are unknown; continue independent authorized work. Do not select `jstack` itself as a leaf worker, route back through it after every step, or create circular requests to escape a blocked dependency.

Finish with the requested outcome, route actually used, artifact revisions and verification, actual external effects, open dependencies, and next owner/action. Distinguish prepared, executed, accepted, and measured results. Persist the checkpoint only in the existing authorized work record; durable memory capture and future monitoring remain separate actions governed by their selected skills and actual grants.
