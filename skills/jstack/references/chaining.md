# Chaining and recovery

## Establish one chain

Use the requested outcome, acceptance criteria, project, current work ID, supplied authority, and resource limits as the root. Reuse its existing records. Choose one coordinator to resolve dependencies and accept the complete result; each specialist owns its deliverable and evidence. Keep scope changes explicit instead of treating a newly discovered opportunity as another authorized initiative.

For each necessary edge, identify the producing and receiving owner, required artifact/revision, permitted data, acceptance, and next action. Record a stable handoff or dependency ID when persistence is useful. Search for the same outstanding dependency before creating another. An acknowledgement is evidence of receipt, not acceptance or completion; a prose owner note is not a lock or a worker.

Identify each selected route as `catalogId:entryId` with its actual scope and source revision, rather than relying on an ambiguous skill name. A chain can mix public and configured private capabilities only within the task's data and authority boundaries. Give a downstream owner the minimum permitted input; selecting a public skill does not make private business facts publishable. Use redacted or synthetic evidence for public outputs unless the user has authorized the identified disclosure.

Prefer a small dependency graph to a fixed pipeline. Parallel work must not write the same resource concurrently or reserve the same budget twice. Use a real supported claim or serialize conflicting writes. A blocker is local until it actually prevents all useful work.

## Example routes

| Request | Smallest useful route and acceptance |
| --- | --- |
| “Show the delivered points for this sprint.” | `scrum-master` alone; deduplicated completed estimates with missing data visible |
| “Publish this finished static guide.” | `web-publisher` alone when the build is ready; deployed revision and real URL checks within the release grant |
| “Test this offer with a landing page and paid media.” | `marketing-factory` coordinates the experiment; `software-factory` only for needed code/instrumentation; `web-publisher` only for the hosting/release work; `ad-buying` for paid execution. Landing verification and tracking are prerequisites for the affected launch; creative preparation can run in parallel. Marketing owns the later outcome decision. |
| “Run this business outcome and improve retention.” | `one-person-company` owns charter, resources, initiatives, and customer responsibilities; selected domain skills execute only the initiatives actually needed. Support evidence may create a software dependency without starting acquisition. |
| “Fix this bug and plan the remaining sprint.” | `software-factory` owns the fix; `scrum-master` uses the resulting scope, readiness, and capacity for sprint decisions. The bug need not wait for a ceremony. |
| “Run the selected organization's paid test using its established workflow.” | Use its applicable configured private specialist first. Add public measurement, publishing, or engineering roles only for actual dependencies, with the same project and permitted data. If the private catalog or selected source cannot be verified, prepare a scoped handoff and hold the affected live action. |

These are examples, not mandatory chains. Reuse working project owners and pipelines; do not add a publishing skill when the established software release already covers the required site delivery. Use `remember` only for an applicable memory action, not as an automatic final stage.

## Gate dependent work on evidence

The receiving owner checks the actual result against its acceptance, target, and source revision. Preserve evidence links and distinguish reported, locally tested, provider-confirmed, and live-verified states. Never accept a success label alone. A revised audience, destination, code artifact, claim, or tracking definition invalidates the affected acceptance and may change the applicable grant; review only the affected scope.

The coordinator keeps the primary outcome and evaluation window intact. Delivering an implementation can close that dependency while retention or experiment measurement remains open. A missing outcome does not authorize redefining the metric or extending spend to obtain a favorable result.

## Resume and recover

On resume, read the current root record, decisions, revisions, remaining resources, and pending effects. Verify current grants and revocations, reconcile unknown external actions, and reuse completed work whose evidence still applies. Resume the next ready node instead of restarting the chain or recreating its tickets.

Reload catalog metadata only when needed to verify a changed selection, source, or scope. If a pinned entrypoint changed, identify the drift and its impact before use; do not update the hash to erase the finding or switch to a same-named global copy. A missing private catalog is not proof that its dependency disappeared. Keep the unresolved private node visible and its public-safe output redacted.

Follow the selected skills' applicable repair limits and the root's time/cost envelope. Without a supplied repair policy, allow one diagnosed repair of a failed handoff, then report the unresolved edge and next decision. A different owner, tool, or route does not reset attempt counts. New evidence can justify a changed plan; repeated requests for the same missing dependency cannot.

Prevent cycles with a root work ID and existing dependency IDs. If A requests B and B needs A's unfinished result, resolve the input contract, split an independently useful slice, or report the circular dependency. Do not create more operators or broader authority to bypass it.

Stop dependent effects on unaccepted inputs, uncertain writes, exhausted resources, revoked authority, or a material regression. Retain useful drafts and continue independent work. Handoff documents do not authorize sending messages to another person or chat, and creating this record does not schedule later execution.
